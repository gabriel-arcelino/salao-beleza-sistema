### O buraco de schema é real e foi reproduzido

Existe `config_comissoes_salon_id_profissional_id_servico_id_key`, UNIQUE em
`(salon_id, profissional_id, servico_id)`. Mas `servico_id` é **nullable**, e no
PostgreSQL NULLs são distintos em índice único. Logo, a unicidade **não protege
o nível profissional** (`servico_id IS NULL`) — justamente a linha que significa
"default do profissional".

Comprovado por inserção: uma segunda config de nível profissional foi inserida
e o índice **não barrou**.

```text
INSERT 0 1
 n_agora | sobre_produto
       2 | {f,t}
```

Consequência: os `on conflict (salon_id, profissional_id, servico_id)` dos
testes `011`, `012` e `013` **nunca disparam** no nível profissional, porque
não há conflito a detectar.

Isto é um **buraco de schemaPreventivo**, não um incidente: hoje não há
duplicata em nenhum ambiente que conte, mas nada impede que surja no primeiro
salvamento repetido pela interface.

```sql
CREATE UNIQUE INDEX config_comissoes_prof_nivel_key
  ON public.config_comissoes (salon_id, profissional_id)
  WHERE servico_id IS NULL;
```

Reforça o finding: os `on conflict (salon_id, profissional_id, servico_id)`
usados nos testes 011, 012 e 013 **nunca disparam** quando `servico_id` é NULL,
porque não há conflito a detectar. Nenhum upsert do projeto protege o nível
profissional.

**Como foi removida:** delete dirigido por `id`, com guardas que só casam se o
estado for exatamente o que foi inspecionado — `servico_id is null`,
`profissional_id = …0101`, `comissao_percentual = 40`,
`comissao_sobre_produto = false`, `created_at = updated_at`.

```text
antes:  config_comissoes = 1   →   depois: config_comissoes = 0
preservados: saloes 1 · profissionais 1 · usuarios 1 · servicos 1 · produtos 1
```

**O que a limpeza NÃO faz:** não fecha o buraco de schema. Sem o índice

é a feature de integridade.

### Decisões que restam, todas de produto

1. **Comportamento do segundo salvamento.** Com o índice parcial, salvar duas
   vezes uma config de nível profissional passa a **erro**. Ou a interface vira
   **upsert** (sobrescreve) — que é o que a API deveria fazer —, ou mostra erro
   ao usuário. Recomendo upsert: salvar uma configuração duas vezes é erro de
   digitação, não intenção de ter duas. **É decisão de produto.**
2. **Existe delete?** Hoje não há, em código nem na interface. Sem delete, uma
   duplicata que já exista é **irremediável pelo aplicativo**. Recomendo criar —
   é a única forma de o usuário corrigir uma config errada hoje.
3. **Ordem entre o índice e o upsert.** Recomendo **upsert primeiro**, índice
   depois: assim nenhuma nova duplicata nasce enquanto a migração não existe. Com
   o índice antes, o segundo salvamento vira erro para o usuário sem que ele
   tenha um caminho para resolver.
